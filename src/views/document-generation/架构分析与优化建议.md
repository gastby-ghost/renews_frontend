## 数据流动过程

### 标准单向数据流（架构原则）

根据项目开发指南，标准的数据流应该是：

```
用户操作
  ↓
组件事件 (Views)
  ↓
Composable (业务逻辑层)
  ↓
Store Action (状态管理层)
  ↓
API服务 (Services)
  ↓
更新状态 → UI响应
```

### AI Agent 工作流

```
Scope Agent → Search2Title Agent → Title Agent → Outline Agent → Body
    ↓              ↓                ↓            ↓           ↓
  研究范围      搜索转标题        标题生成       大纲生成      正文
```

**各Agent职责**:

- **Scope Agent**: 定义研究范围和简报
- **Search2Title Agent**: 基于研究结果生成标题候选
- **Title Agent**: 优化和筛选标题
- **Outline Agent**: 生成文档大纲
- **Material Bind**: 绑定素材到章节

## 当前存在的问题

### 1. ❌ 违反单一职责原则

**问题描述**: `useOutlinePage.ts`承担过多职责

**证据**:

- 文件大小: 1200+ 行
- 职责混合:
  - 业务逻辑：大纲生成、AI绑定
  - 状态管理：调用5+个Store
  - 数据转换：API请求数据格式化
  - UI控制：进度、加载状态管理

**代码示例**:

```typescript

  // 业务逻辑 (大纲生成)

  const bindMaterialsWithAI = async () => { ... }

  // 数据转换
```

**影响**:

- ❌ 可维护性差
- ❌ 测试困难
- ❌ 职责不清
- ❌ 代码复用性低

### 4. ⚡ 统一异步任务处理

**目标**: 抽象通用轮询逻辑

**创建通用Hook**:

```typescript
// useAsyncTask.ts
export function useAsyncTask<T>() {
  const loading = ref(false)
  const progress = ref(0)
  const error = ref<string | null>(null)
  const result = ref<T | null>(null)

  const execute = async (
    task: () => Promise<PollingTask>,
    onProgress?: (progress: number) => void
  ) => {
    loading.value = true
    error.value = null

    try {
      const poller = await task()

      poller.on('progress', (status) => {
        progress.value = status.data.progress
        onProgress?.(status.data.progress)
      })

      const finalStatus = await poller.promise
      result.value = finalStatus.data

      return finalStatus
    } catch (err) {
      error.value = err instanceof Error ? err.message : '任务执行失败'
      throw err
    } finally {
      loading.value = false
    }
  }

  return {
    loading: readonly(loading),
    progress: readonly(progress),
    error: readonly(error),
    result: readonly(result),
    execute
  }
}
```

**使用示例**:

```typescript

  return await execute(

  )
```

### 6. 🎨 业务逻辑提取

**目标**: 将计算逻辑移到composables

**提取示例**:

```typescript
// composables/outline/useOutlineBinding.ts
export function useOutlineBinding() {
  /**
   * 获取章节的绑定素材
   */
  const getSectionBindings = (
    sectionIndex: number,
    bindingResult: MaterialBindResult | null
  ): MaterialBinding | undefined => {
    if (!bindingResult) return undefined
    return bindingResult.material_section_bindings.find(
      (binding) => binding.section_id === sectionIndex + 1
    )
  }

  /**
   * 获取章节的平均匹配分数
   */
  const getAverageMatchScore = (
    sectionIndex: number,
    bindingResult: MaterialBindResult | null
  ): number => {
    const bindings = getSectionBindings(sectionIndex, bindingResult)
    if (!bindings || bindings.match_scores.length === 0) return 0
    const average =
      bindings.match_scores.reduce((sum, score) => sum + score, 0) / bindings.match_scores.length
    return Math.round(average)
  }

  /**
   * 获取可用素材
   */
  const getAvailableMaterials = (
    sectionIndex: number,
    allMaterials: Material[],
    outline: OutlineSection[],
    bindingResult: MaterialBindResult | null
  ): Material[] => {
    const section = outline[sectionIndex]
    if (!section) return []

    const boundMaterials = new Set(section.data_requirements || [])

    // 排除AI已绑定的素材
    const aiBindings = getSectionBindings(sectionIndex, bindingResult)
    if (aiBindings) {
      aiBindings.materials.forEach((material) => {
        boundMaterials.add(material.title)
      })
    }

    return allMaterials.filter((material) => !boundMaterials.has(material.title))
  }

  return {
    getSectionBindings,
    getAverageMatchScore,
    getAvailableMaterials
  }
}
```

**组件中使用**:


## 总结

当前`document-generation`模块虽然在功能上可以工作，但在架构设计上**严重偏离**了项目开发指南的要求。主要问题集中在：

1. **分层架构混乱** - 组件、Composables、Store职责不清
2. **单向数据流断裂** - 多层状态同步导致数据流复杂
3. **代码耦合严重** - 违反单一职责原则
4. **类型安全保障不足** - 大量使用any

通过实施本优化方案，将实现：

✅ **清晰的分层架构** - 每层职责单一 ✅ **单向数据流** - 数据流向清晰可预测 ✅ **高内聚低耦合** - 代码复用性高 ✅ **类型安全** - TypeScript严格类型检查✅ **易于维护** - 代码结构清晰 ✅ **易于测试** - 单一职责便于单元测试
